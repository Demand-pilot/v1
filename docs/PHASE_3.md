# Phase 3 — Real Training, Persistence, and Inference

**Status:** not started
**Gate:** GATE 3
**Depends on:** Phase 2 (canonical adapter, `DatasetProfile`, CORE/OPTIONAL feature split)

This is the core deliverable. It is the phase that makes "predict the upcoming values"
true, and it is the largest of the five.

---

## 1. Objective

Given a dataset, produce genuine `h = 1..16` day-ahead forecasts for the period
immediately following the last observed date, generated by a **model persisted on disk**,
loadable by a **fresh process**, with an honest, leakage-free accuracy estimate.

Today there is no inference path at all. There is no `torch.save`, no `joblib.dump`, no
`lgb.Booster.save_model`, and no checkpoint loading anywhere in the repository. Models
were fit in-process and discarded.

---

## 3. The leakage design (mandatory)

**Single global direct model with horizon-safe lags.**

- Build features only from `df[df.date <= cutoff]`.
- Use exclusively lags/rollings at offset ≥ `H`: `lag_16, lag_21, lag_28, lag_35`,
  `rolling_mean_16d/28d/56d`, `rolling_std_28d`, `zero_ratio_56d`.
- Emit one training row per `(series, cutoff, h)` with `horizon_day` as an explicit
  feature.
- Calendar and config-declared exogenous features are computed for the **target date**
  `cutoff + h`.
- Promo for `cutoff + h` is legal only when the config declares
  `promo_known_in_advance: true`.

Expect measured RMSLE to land **worse** than the fabricated 0.42393. That is the correct
outcome and must be reported as such.

> **Recorded, not built:** 16 direct per-horizon models (`model_h`) would let `h = 1` use
> `lag_1` instead of the conservative `lag_16`, typically buying 3–8% RMSLE. Note it in
> the ADR; ship the single model first.

### Open question carried in from Phase 2

`delta_oil` is currently aligned to the **target date**, which by the policy's own rule is
leakage — `delta_oil` at `cutoff + 16` is not knowable at the cutoff. Phase 3 does not
resolve this. It must:

- keep `delta_oil` separable in the feature set, and
- ensure Phase 4 can measure its contribution in isolation,

so the decision (shift by `H`, or gate behind a per-exogenous `known_in_advance` flag) is
made on evidence in Phase 4. Marked `TODO(blocked)` in `docs/LEAKAGE_POLICY.md`.


```
  booster.txt              # lgb.Booster.save_model()

```

`feature_schema.json` **must** capture categorical level vocabularies — this is what makes
inference on unseen entities/items *detectable* rather than silently wrong. Phase 2
already produces these via `DatasetProfile.entity_vocabulary` / `item_vocabulary`.

Add a **schema hash**. `load_model` refuses to predict when the incoming feature frame's
hash differs — raise `FeatureSchemaMismatchError` (already defined in
`src/models/exceptions.py`).

### 4.3 `src/inference/predictor.py` — new

```python
class Predictor:
    def __init__(self, run_id: str): ...
    def predict_horizon(
        self,
        history: pd.DataFrame,                      # canonical, dates <= cutoff
        cutoff: pd.Timestamp,
        horizon: int = 16,
        future_known: pd.DataFrame | None = None,   # e.g. published promo schedule
    ) -> pd.DataFrame:
        """entity_id, item_id, date, horizon_day, yhat, engine, run_id, is_cold_start"""
```

Behaviour:

- **Unseen categoricals** → `is_cold_start=True`, route to cold-start policy. Do not let
  LightGBM bin an unknown category alongside a known one. (`entity_code == -1` already
  signals this.)
- **Insufficient history** → series with `< H + 28` days cannot form lags → cold start.
- **Zero series** → entire observed history zero → forecast `0.0`, engine `ZERO_MASK`,
  **derived at runtime** from `DatasetProfile.permanent_zero_series`, never a hardcoded
  count. Log the actual number; do not assert 53.
- **Closures** → apply `closures` from the dataset config, then `clip(0, None)`. No
  `store 25` literal in code — the exemption is already `except: ["25"]` in
  `favorita.yaml`.

### 4.4 `src/inference/cold_start.py` — new

Ordered fallback. The chosen tier must be returned so the UI can display it.

| History | Strategy |
|---|---|
| `>= 44 days` | Full model |
| `14–43 days` | Item-level pooled model (same `item_id`, other entities), scaled by the entity's observed volume ratio |
| `1–13 days` | Seasonal naive on whatever exists, wide interval |
| `0 days` | Item-level median across entities. **Item also unseen → return `None`, reason `"insufficient_history"`.** Do not invent a number. |

### 4.5 `scripts/train_pipeline.py` — rewrite

```bash
python -m scripts.train_pipeline \
    --dataset configs/datasets/favorita.yaml \
    --cutoff auto \
    --horizon 16 \
    --engines lightgbm,lstm,seasonal_naive,croston \
```

Must: load via adapter → profile series → build horizon-safe features → train each engine

of `2017-08-16 .. 2017-08-31` — **derived, never hardcoded.** Phase 1 already removed
those literals from `intent_router.py`, `database.py`, and the API schema; do not
reintroduce them.

## 5. GATE 3

1. `python -m scripts.train_pipeline --dataset configs/datasets/favorita.yaml --cutoff auto`
   produces `artifacts/models/{run_id}/booster.txt` **on disk**.
2. A **fresh process** loads that `run_id` and produces 16-day forecasts for
   `2017-08-16..2017-08-31` without re-reading `train.csv` for training.
3. `GET /api/v1/forecast/grid` returns those forecasts, and every value is traceable to
   `booster.predict(...)`.
4. The synthetic 3×2×400 dataset from GATE 2 trains and forecasts end-to-end **with no
   code changes — only a new YAML config.**

### Blocker

Items **1–3 require `data/train.csv`** (3,000,888 rows) plus `stores.csv` and `oil.csv`.
`data/` is currently empty; the Favorita CSVs are gitignored by size.

Item **4 has no such dependency** and can be closed immediately.
